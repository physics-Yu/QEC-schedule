# 中性原子软件的测试 回退与发布流程

日期：2026-10-19。状态：拟采用流程；本文不代表远程规则或工作流已经启用。配套：[系统设计](full-stack-rfc.md)、[核查记录](baseline-2026-10-19.md)。

目标是让一次改动具有明确需求、可复现测试、可审查差异、可撤回交付，以及可追溯发布。GitHub 保存决策、变更与验证证据；聊天用于讨论，不承担唯一项目状态。

## 1. 从需求到合入

每个交付记录问题、使用者、输入输出、非目标、受影响接口、验收、预算和回退办法。跨层语义变化先提交 RFC/ADR；局部缺陷不强制写额外设计文档。

流程为 `issue → 工作分支 → draft PR → 验证 → 审查 → develop`。RFC 接受后形成 accepted ADR；后续改变以新 ADR 替代，保留原因与兼容处理。文档审查不能冒充实现或实验验收。

`main` 保存已发布基线，`develop` 是集成分支，工作分支从最新 develop 创建，Codex 分支使用 `codex/<topic>`。普通 PR 可 squash；release、hotfix 和基线同步需明确保留祖先关系的合并方案，不同时强制“所有合并 squash”和“长期分支必须包含对方全部提交”。

当前 main 比 develop 多 15 个提交，差异仅为三个文档/图文件。应作为独立同步变更审查，不与核心重构混在一起；再次执行时重新核对 refs。同步成功不能写成“代码功能已经更新”。

第一版不引入 release-please 与人工 release 分支双重版本管理。由一个发布 PR 维护版本和 changelog，验收完成后合入 main、在该提交打不可移动的 tag；之后同步回 develop。稳定分支数量增加时再引入专门 release 分支。

## 2. P0 先建立真实基线

1. 固定 commit、Python、平台、依赖版本和测试发现规则；生成测试 ID 清单，防止发现零测试却显示通过。
2. 在独立环境安装 wheel 并运行入口 smoke，确认 viewer 等包数据和可选插件安装完整；测试不能只靠源码路径上的 import 成功。
3. 按测试 ID 登记失败：产品缺陷、缺依赖、缺夹具、平台不适用、历史实验。记录负责人、恢复条件与期限。
4. 恢复具有合法来源的小夹具；大数据以校验和索引下载到隔离缓存。禁止为凑绿灯伪造旧实验产物或无条件 skip。
5. 仅允许显式的已知失败清单，禁止新增失败、未知 skip 或意外 XPASS 静默通过。发布所承诺能力涉及的套件不能留未解决豁免。

核心无 extras 环境可测试“插件缺失时诊断正确”。完整矩阵须安装声明支持的 extras，并对这些测试禁止依赖缺失 skip。旧套件继续运行；不把删除旧测试当作消除回归。

## 3. 按风险建立验证层次

| 套件 | 验证内容 | 合入与发布要求 |
|---|---|---|
| 基础与契约 | 单位、身份、序列化、版本、能力、命令回执 | 每个相关 PR；失败阻断 |
| 领域语义 | lowering 等价、测量映射、帧、资源守恒、几何与时序 | 相应模块 PR；随机合法与非法输入均覆盖 |
| 插件符合性 | 拒绝不支持能力、预算耗尽、配置、确定性声明 | 每个正式支持的插件都必须执行 |
| 运行故障 | 重复提交、事件重复/缺口、断线、过期 epoch、取消、解码延迟 | runtime/backend PR 与发布前 |
| 纵向集成 | 小程序→计划→执行→结果；QEC memory；资源生产→消费 | develop 所承诺功能的必要闸门 |
| 旧行为回归 | 源操作终态、因果关系、实际资源、选定结果 | 迁移相关 PR；以冻结输入和语义投影比较 |
| 科学基准 | 逻辑错误率、吞吐、编译成本、运行时间与失败率 | 发布候选；声明 shots/布局/种子/区间/拒收口径 |
| 硬件在环 | 时钟、控制回执、停止、观测延迟与模型偏差 | 仅受控环境；不能由模拟桩替代 |

固定事件哈希适合相同实现的确定性回归。算法或事件表示改变时，使用独立定义的语义比较；不能要求所有优化永远保持旧时间与旧窗口数。新黄金基线必须解释变化、提供对照证据并由审查接受。

随机性能回归预设统计判据、预算和硬件条件；单次“慢了 20%”先作为调查信号。异质噪声实验按独立布局估计不确定性，不把同一布局内全部 shots 当作独立样本。

## 4. CI 与 GitHub 闸门

建议按实施顺序引入以下检查名，先完成可重现运行，再设为 required：

| 检查 | 内容 |
|---|---|
| `quality` | 新代码 lint/type、依赖方向、契约/文档一致性；旧代码按明确范围逐步收紧 |
| `core-tests` | 核心与契约、测试清单、skip/失败预算 |
| `plugin-tests` | 锁定 extras，插件符合性与所需集成 |
| `wheel-smoke` | 构建并在新环境安装 wheel，从源码目录之外运行 |
| `integration` | 纵向切片与规定的旧行为回归 |
| `release-qualification` | 对精确发布 commit 运行完整目标套件、基准与回退演练 |

PR 和 develop 推送运行快速矩阵；长期科学基准由夜间/手动工作流运行。发布必须引用对应候选 commit 与依赖锁的结果，不能拿旧 nightly 的绿灯替代。启用 merge queue 时同时覆盖 `merge_group` 触发，否则待合并提交可能没有检查。

分支规则要求 PR、唯一命名的必需检查、解决审查意见、禁止强推和删除。合并由维护者执行；AI 创建或更新 PR 不自动获得合并权限。若只有一位维护者且提交也由同一 GitHub 身份产生，需采用实际可执行的审查约定，不能配置必须由不存在的第二人批准而锁死项目。

CI 是必要条件，接口设计审查、科学范围判断与发布决策同样是闸门。文件中写下规则不等于 GitHub 已配置；远程规则的启用需独立核对。

工作流默认只读权限，第三方 Actions 固定完整 commit SHA，PR 代码不获得硬件凭据；发布凭据仅在受保护的发布环境使用。依赖锁与版本化数据索引进入仓库，运行产物进入独立存储并设置保留策略。[GitHub 分支保护](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)；[Actions 安全配置](https://docs.github.com/en/actions/reference/security/secure-use)。

## 5. 发布与回退

发布包包括 wheel/sdist、源码 commit、依赖锁、schema/协议兼容表、默认插件及版本、设备/模型样例、验收报告、changelog、输入与产物校验和。软件包版本、契约版本、设备快照和实验运行身份分别管理。

发布顺序：冻结候选 → 对该 commit 验证 → 从干净环境安装并试运行 → 演练回退 → 维护者合入/tag → 发布已验证产物及其哈希 → 回读 Release 与安装验证。若合并产生不同 commit，需验证该精确提交；不能把未经测试的重建结果直接代替候选。

| 回退对象 | 实施方式 | 保证边界 |
|---|---|---|
| 源码变更 | revert PR，重新运行检查 | 保留历史，不强推共享分支 |
| 算法插件 | 回到已验证版本与配置，重新做能力/输入兼容检查 | 改配置本身不保证旧插件能读新 IR |
| 发布环境 | 恢复上一份锁定的发布清单与兼容数据 | 不仅固定一个 Python 包版本 |
| schema/数据 | 保留原件与迁移记录；按可用读者/写者版本回退 | 迁移未必可逆；明确禁止不支持的降级 |
| 运行会话 | 查询回执与提交前沿，停止、补偿或重建 | 已执行物理动作不可通过代码回滚撤销 |
| 科学结果 | 原始数据不变，发布更正与新分析版本 | 不覆盖原结论的输入与证据 |

回退演练必须包含：旧版本读取保留的数据、恢复默认插件、一次提交结果未知时的核对、一次受控取消。回放已记录事件与重新进行随机实验是不同操作。

## 6. 首批独立交付

1. **架构审查包（本轮）**：系统边界、旧草案修订、运行契约、外部方案与可核查基线。
2. **基线同步 PR**：main 的文档同步到 develop，重新核对差异与祖先关系。
3. **可复现测试 PR**：测试发现清单、依赖环境、失败归因与最小 wheel smoke；不改业务语义。
4. **工程闸门 PR**：CI、PR/issue 模板、CONTRIBUTING、AGENTS.md 与 accepted ADR 的链接，远程规则验证。
5. **P1 最小契约 PR**：身份/时间/快照/能力/证据与命令事件模型，配合真实消费者的合同测试。
6. **P2 纵向切片 PR**：一个小程序及两种受限后端、反馈、取消、回放与恢复。

每批交付可单独验收与回退，不以固定行数替代完整性判断。复用库的技术验证先于完整编译框架实现；旧代码退役必须列出已接管的行为与未迁移的能力。
