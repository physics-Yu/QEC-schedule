# 扩大候选池、并行编译与不归还初态优化

2026-09-21。用户明确要求扩大候选池、并行搜索编译，暂不考虑放回原layout。本轮保留既有物理约束，新增显式结束条件，并实际省去末尾归还操作。

## 当前默认与兼容

新工作台草稿：`proposal_pool=256`（此前64），`evaluations=16`（复杂对照此前6），`workers=4`，`terminal_mode=stable`，每候选编译限时180s。池大小表示每轮便宜的布局提案数量上限；16表示完整实际评估总数，包含顺序基线、失败及重放。不是将256份候选全部物理编译，也不承诺四倍墙钟加速。

结束条件有两个：

- `stable`：完整电路及已接受物理服务执行完毕，无待执行事件、无交接过程、AOD静止，支撑/物理规则通过。停止时可在不同合法位置，**不再执行末尾恢复原layout、AOD轴及原SLM开关**。
- `fixed`：保留历史共同绝对终态，即顺序基线的holder、AOD与开关。

两种模式均保留**每批CZ后分离、返回该批抓取点并卸载**，测量服务的内部归还也未改变。因此稳定完成时间不一定等于最后光门的结束时间；末门若为CZ，其服务后处理仍计入。不是简单减掉原报告里的若干微秒，更不是在最后脉冲处截断动画。初始化装配成本仍不计，环境运行中不重新安装mapping。

旧JSON缺少三个新增字段时按 `64/1/fixed` 解释；历史结果打开时保留原合同。新草稿可由“载入8原子对照示例”建立。低层API继续默认固定终态、单进程以保持兼容，新模式需显式传入。

## 并行机制

`placement/verified.py`按固定序号挑选一批不同候选：256提案中优先取交互距离较短者，同时保留每第三次的随机探索。整批都从同一已知最佳布局构造，返回后依输入顺序更新最佳，平局保留先前结果。批次改变了反馈频率，因此不保证与逐个更新的串行搜索走同一路径；测试比较的是**相同批次**的串行/并行。

`app/placement_execution.py`用 `ProcessPoolExecutor` 和显式spawn运行最多4个独立Python进程，绕过Python线程的GIL限制。主进程预先分配候选编号与独立文件夹；每个worker从独立初始snapshot恢复env，编译、执行、检查门效果及结束条件，并独立重放。所有运行态改变仍通过env提交/推进，不共享live env。

`placement_worker.py`是可序列化的进程入口。进程只收snapshot、候选映射及固定合同，不依赖浏览器；自定义协议检查回调留在父进程，故可使用lambda/closure。Windows CLI入口增加main保护，避免子进程重启服务器或递归启动实验。

每份候选的 `result.json` 保存PID、开始/结束时间、编译和重放耗时。批次里的失败保留记录，不能替换合法基线。配置允许1–8 worker；平台、并行数和超时会影响实际吞吐，不能用CPU数量直接当实测加速比。

每例16/16候选通过，共32/32。12原子胜者#5为交换候选；16原子胜者#1为交互图构造候选。两组各有4个不同PID，独立开始/结束时间证实峰值4个worker重叠运行。所有候选均检查门恰好一次、完整实际计划重放、无pending事件及合法稳定终态；两版最终位置确实不同。

搜索与两份动画录制墙钟分别514.82s、613.35s。它们比此前6候选实验评估更多布局，且目标改变；不能据此直接计算并行加速比。当前整批屏障受最慢候选限制，少数探索候选明显更慢；后续可考虑基于已执行时间下界的安全剪枝和更充分的任务队列调度，本轮未宣称实现。

这两个例子末门为1Q，故稳定完成时间恰等于最后一个门完成时间；末门CZ的测试明确验证其回程/卸载仍计时。收益来自新结束合同下的实际运输改进，不能混用旧含末尾归还总时间作为分母。
