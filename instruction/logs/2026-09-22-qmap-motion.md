# QMAP 运动展开修正

用户指出运动难看、不合理；本轮从 2026-09-21 夜间开始，跨日完成。先按地址栏误定位到旧16原子任务，实际读取浏览器后确认用户已编辑为9原子12门，停在733.86μs、Q005移动。旧 URL 没随编辑编译改变。未覆盖用户页面或草稿，改用新页交付。

## 根因

旧 adapter 把作者每个中间路标当成必须到达的位置，再分别 XY/YX 展开；虽然通过物理校验，却没有检查折点是否必要。闲置 AOD 轴还会按当前载荷重新收拢。原16例作者173条move变为445段（空载86段），这是策略/兼容层问题，不是浏览器渲染。

用户当前9例 Q005 起点(0,10)、终点(21,60)。旧路径：

`(0,10) → (5,10) → (5,15) → (15,15) → (15,50) → (21,50) → (21,60)`。

只试起终点XY/YX无法解决，因为源行/列上有其他原子；还必须保留逃逸通道。最终通过连续校验的路径：

`(0,10) → (5,10) → (5,60) → (21,60)`。

先从源列取出，再沿空通道直行，最后到达原目标；转弯仍有真实停点。没有改变物理硬规则、SLM布置、AOD容量、CZ批次或装卸目标。

## 实现

- `strategies/qmap_native/adapter.py`：连续move序列合并考虑，只在load/store/门操作处固定边界；候选包含直接正交路径及经作者路标/逃逸角点的路径，合并同轴冗余点，按本地运动时长排序，逐候选做完整扫掠验证。不合法则保留既有路线作为后备，不把失败probe提交到live env。
- 空闲行列采用原坐标的有序约束投影，仅在载荷轴强制让位时移动。关闭轴不再无条件跟着载荷收拢，但间距和行列序关系仍检查。
- `simplify_motion=False` 仅为低层复现入口，不增加工作台菜单。原生C++调度/placement没有改，也未重新选择有利native输出。
- viewer 的“目标伙伴”修正：批次requested原子列表不是伙伴列表；优先从实际/下一次CZ配对取伙伴。Q005此时应显示Q003，不能显示另外8个原子。
- app已有worker每次导入新策略，当前服务50860可继续手动编辑编译；原页面保留，修正版job `0f8e034ad4804a49a92436301f1a8c1d`。
