# 开发、日志与稳定交接

用途：开始/结束任务、跨会话交接、变更规范时读取。常驻行为准则位于 [agent.md](../agent.md)。

## 1. 三层信息，不重复全量读取

1. `agent.md`：稳定行为、职责边界、按任务选读路由；不堆历史日志与论文摘要。
2. `instruction/*.md`：按领域的规范与现状；`handoff.md` 是短的最新工作状态。
3. `instruction/logs/`、`references/`：历史证据和来源，只在追溯具体问题时读对应文件。

`AGENTS.md` 仅作自动发现入口，指向 agent/handoff，不维护第二套规范。原 architecture 根路径保留短导航，全文位于 references；全量历史不作为默认上下文。

## 2. 开始工作

- 读 agent/handoff，明确最近的用户决策、当前 milestone 和 OPEN 问题。
- 从索引选 1–3 个相关模块，读源码后确认接口确实存在；不要直接照历史示例调用虚构方法。
- 说明本轮要完成的具体行为与验收范围。发现规范/代码/文献冲突时使用 model_audit 分类，不默认扩大物理模型。
- 大任务开始就建立本轮日志草稿，状态记 `IN_PROGRESS`；中断时留下已完成部分与下一步，不等最后才写。

## 3. 进行中

按依赖顺序改动，校验应围绕行为而不是镜像实现。保持用户已授权的任务范围；独立子任务只有明确要求时才委派。

记录重要决定：采用什么简化、为什么、何时不再适用。硬件数值改变注明来源、单位、影响哪些旧预期；视觉修改不改变物理配置。

新发现的问题可以列 OPEN，但不能在最终交接中省略；用户请求的范围若是文档审计，不静默加入未说明的运行时代码重构。

## 4. 完成/中断

日志状态使用 `COMPLETED`（本轮目标完成）、`PARTIAL`（有剩余）、`BLOCKED`（需外部条件），不要把里程碑状态与单次文档任务状态混淆。

每次结束更新：

- 相关 instruction 中的当前 API/限制。
- 本轮日志的最终状态、验证命令/结果、未验证部分。
- `handoff.md` 的当前摘要、OPEN 问题和最新日志链接。
- 如修复问题，在 `model_audit.md` 保留问题 ID，标 FIXED 并链接证据。

已完成日志追加更正或写新日志，不覆盖历史事实。不为同一主题复制多个“当前规范”；日志只引用规范。

## 5. 日志模板

建议文件名：`YYYY-MM-DD-主题.md`；同日多次用有意义的主题或序号区分。

```markdown
# 日期 · 任务主题

- 状态：IN_PROGRESS / COMPLETED / PARTIAL / BLOCKED
- 用户目标与本轮范围：
- 开始时的 milestone / 基线：
- 相关 instruction：

## 完成内容
- 修改文件、行为及原因；不以工具调用流水账充数。

## 验证
| 命令/检查 | 本轮结果 | 证据路径或关键数字 |
| --- | --- | --- |

## 决策与物理假设
- 用户决策 / 文献依据 / 工程简化分别说明。

## 未完成与风险
- 问题 ID、触发条件、是否影响当前验收；没有运行的检查。

## 下一步
1. 下一项可直接执行的任务、入口文件、完成条件。

## 可复现信息
- 配置/seed、源码版本或指纹、运行环境；产物可重新生成的命令。
```

## 6. 当前状态摘要的内容上限

`handoff.md` 只保留：当前阶段、已完成能力、关键指标、最重要 OPEN 项、下一步、验证证据链接。保持可在一次短读取中理解；详细来源和复现放其他文件。新增日志后不要把全部历史正文粘到 handoff。

## 7. 文件与证据检查

文档拆分需校验原文归档字节一致、章节映射完整、相对链接与锚点存在。日志中的产物一般在 `.gitignore` 内，跨机器交接必须有可重建命令和文字关键结果。

行为变更运行相关测试；更换 schema 验证合法恢复和损坏输入；视觉改动检查实际产物，浏览器无法验收则明确标记，不用离线替身结果冒充。
